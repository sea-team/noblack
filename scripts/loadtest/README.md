# noblack 并发压测工具

单文件、零第三方依赖的 Go 压测工具，针对 noblack 服务的检测链路设计。

默认走**阶梯递增 + 自动熔断**，失败率或 P99 超阈值时立即停止，避免把线上压挂。

---

## 快速开始

### Windows

```powershell
cd D:\work\project\go\noblack\scripts\loadtest
go build -o loadtest.exe .

# 先跑网络基线，拿到你这边的网络地板
.\loadtest.exe -url https://noblack.guanliyuangong.com -token <令牌> -scene baseline

# 再跑阶梯压测
.\loadtest.exe -url https://noblack.guanliyuangong.com -token <令牌>
```

### Linux / macOS

```bash
cd scripts/loadtest
go run . -url https://noblack.guanliyuangong.com -token <令牌>

# 或编译后反复使用
go build -o loadtest . && ./loadtest -url https://... -token <令牌>
```

### 代理环境

Go 的 HTTP 客户端默认读取 `HTTP_PROXY` / `HTTPS_PROXY` 环境变量。若目标域名确实经代理转发，测出的延迟会包含代理开销，压测前可以清掉：

注意 Go 同时识别**大写和小写**两套变量（`HTTP_PROXY` 与 `http_proxy`），只清一套不生效：

```powershell
# Windows PowerShell
$env:HTTP_PROXY=""; $env:HTTPS_PROXY=""
$env:http_proxy=""; $env:https_proxy=""
.\loadtest.exe -url https://noblack.guanliyuangong.com -token <令牌>
```

```bash
# Linux / macOS
env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy \
  ./loadtest -url https://... -token <令牌>
```

确认代理是否真的影响了结果：清空前后各跑一次 `-scene baseline` 对比。若两次数字接近，说明该域名本就不走代理（在直连规则里，或代理透明转发），此时 `/health` 的延迟就是真实网络往返。

## 六种场景

用 `-scene` 选择，默认 `ramp`。

| 场景 | 作用 | 典型用途 |
|------|------|----------|
| `ramp`（默认） | 并发逐级递增，找吞吐拐点 | 容量规划、上线前验收 |
| `baseline` | 只压 `/health`，不碰模型与词库 | **必先跑**，剥离网络往返开销 |
| `modes` | 五种检测模式横向对比 + 召回开关代价 | 选型：该用哪个 `NB_DETECT_MODE` |
| `textlen` | 20 / 100 / 500 字对耗时的影响 | 评估长文本场景的容量 |
| `soak` | 低并发长时间跑，观察延迟是否劣化 | 查连接泄漏、内存增长 |
| `all` | 依次全跑 | 完整体检 |

### 为什么必须先跑 baseline

`/health` 只返回内存里的计数，不碰词库和模型，它的耗时就是**网络往返的下限**。

实测例子：访问线上时 `/health` 单次 curl 要 1.2 秒，但连接复用后只要 33ms —— 那 1.2 秒几乎全是 TLS 握手，与服务能力无关。本工具默认复用连接，所以测出的是稳态延迟。不先拿到这个地板，会把网络往返误读成服务慢。

同样重要的是**吞吐对照**：实测 `/health` 在并发 32 下能到 1017 QPS，而 `/check` 只有 156 QPS。两者走同样的网络，因此差异来自服务端而非网络。

## 参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `-url` | `https://noblack.guanliyuangong.com` | 服务地址，**不含路径** |
| `-token` | 空 | 鉴权令牌，走 `X-Auth-Token` 头 |
| `-scene` | `ramp` | 场景，见上表 |
| `-steps` | `1,2,4,8` | 阶梯并发数，逗号分隔 |
| `-step-dur` | `15s` | 每级持续时长 |
| `-timeout` | `30s` | 单请求超时 |
| `-max-fail` | `5` | 熔断：失败率上限（%） |
| `-max-p99` | `10s` | 熔断：P99 上限 |
| `-no-abort` | 关 | 关闭熔断，压满全部阶梯 |
| `-insecure` | 关 | 跳过 TLS 证书校验（自签证书用） |
| `-soak-conc` | `2` | soak 场景的并发数 |
| `-soak-dur` | `5m` | soak 场景总时长 |
| `-soak-every` | `30s` | soak 场景汇报间隔 |

未提供 `-token` 时，若服务端启用了检测鉴权，探测阶段就会因 401 直接退出，不会带着坏令牌空压。

## 熔断保护

默认开启，两个条件任一触发就停止加压：

- 失败率 > 5%（`-max-fail`）
- P99 > 10 秒（`-max-p99`）

级与级之间还有 2 秒冷却，让服务喘口气。

**压生产环境建议收紧**：

```bash
./loadtest -url https://... -token <令牌> -max-fail 3 -max-p99 3s
```

确认安全阈值后要压满全部阶梯，才用 `-no-abort`。

## 读懂输出

```
=== 服务探测 ===
  /health      : {"code":200,...,"word_count":64552}
  /auth/status : {"code":200,...,"detect_required":true,"required":true}
  检测模式     : model_first | 模型结果: 1 个 | 首次往返: 37.6ms
      模型 lite     服务端自报耗时 2.5ms
  ⚠ 线上启用了 AI 模型: 模型链路吞吐远低于词库, 高并发会让真实用户延迟到秒级。

=== 阶梯压测 (阶梯递增, 每级 12s) ===
场景            并发    QPS      平均      P50      P95      P99   失败率   成功数
并发8            8    145.3   54.9ms   52.1ms   77.6ms   94.2ms  0.00%     1744
    服务端自报推理 6.3ms (双模型并行取较慢者), 客户端 P50 52.1ms
```

**「服务端自报推理」与「客户端 P50」是两个不同分布，工具不做减法。**

前者是模型推理的纯耗时（多模型并行时取较慢者），后者还包含网络往返、代理转发（若有）和服务端排队。两者取自不同分布，相减会得出负数之类的无意义结果。并列展示，由你判断瓶颈在哪：

- 两者接近 → 瓶颈在推理
- 客户端 P50 远大于自报推理，且随并发上升而线性增长 → 瓶颈在排队（连接管理、线程池），加机器比调模型有效

## 判断是否饱和

看**吞吐是否还随并发增长**：

- 吞吐随并发线性增长 → 未饱和，继续加压
- 吞吐持平、延迟线性增长 → **已饱和**，这就是容量上限
- 吞吐随并发**下降** → 出现锁竞争或资源耗尽，需要排查

线上实测例（单模型 lite，网络往返约 33ms）：

| 并发 | 1 | 2 | 4 | 8 | 16 | 32 | 64 |
|---|---:|---:|---:|---:|---:|---:|---:|
| QPS | 25 | 49 | 92 | 145 | **160** | 156 | 158 |
| P50 | 37ms | 37ms | 39ms | 52ms | 97ms | 192ms | 341ms |

并发 16 是拐点，约 160 QPS。之后吞吐持平、延迟等比例增长 —— 典型排队饱和。

## 压生产环境的注意事项

**先确认服务端的检测模式**。探测阶段会打印，若含 AI 模型会给出警告。

模型链路的吞吐远低于词库链路。实测本地环境：

| 模式 | QPS | 相对词库 |
|---|---:|---:|
| `word_only` | 14,879 | 基准 |
| `model_first` / `both` | 9 | **1/1650** |

双模型部署时并发 2 即饱和，并发 32 时 P50 达 3.6 秒 —— **真实用户会明显卡顿**。改用单模型（服务端 `NB_MODELS=lite`）后线上可达 160 QPS。

因此压生产前：

1. 先用 `-scene baseline` 拿网络地板
2. 从 `-steps 1,2,4` 小并发起步，别一上来打满
3. 保持熔断开启，必要时用 `-max-p99 3s` 收紧
4. 观察真实用户是否受影响，随时可 Ctrl+C 中止

## 级间冷却与恢复等待

高并发压测结束后，本机与服务端的连接不会立刻释放。**不等它们清空就开下一级，测出的是"服务还没缓过来"的数字，而不是真实容量。**

这正是"并发 400 比 1000 跑得还快"这类反直觉结果的主因 —— 1000 那一级是在 400 的残留压力下测的。

工具已内置两道保护：

**1. 自适应冷却**（按刚跑完的并发量）

| 并发 | 冷却时长 |
|---:|---:|
| < 64 | 2s |
| 64–199 | 6s |
| 200–499 | 12s |
| ≥ 500 | 20s |

**2. 恢复等待**（并发 ≥ 64 时）

冷却后用一个全新连接（禁用 keep-alive）实测 `/health`，响应正常才继续，最多等 60 秒。等不到会明确告警：

```
  冷却 12s (并发 400 的连接需要时间释放)...
  等待服务恢复中... (第 1 次探测未通过)
  ⚠ 等待 1m0s 服务仍未恢复, 继续下一级 (结果可能偏低)
```

看到这条告警时，**后续数据不可信**，应加大 `-step-dur` 间隔或分批手工跑。

**3. 探测重试**

启动时的健康检查带 3 次退避重试（2s / 4s / 8s），避免刚跑完压测就因连接未释放而误判"服务挂了"。

### 手工分批更可靠

连续跑超高并发（≥400）时，即便有上述保护，服务也可能需要 1-2 分钟才能完全恢复。实测线上 400 并发后，健康检查耗时从 33ms 劣化到 3.6 秒，持续一分多钟。

要测多个高并发档位，**分开跑并留足间隔**比一次跑完更可信：

```bash
./loadtest -url https://... -token <令牌> -steps 400 -step-dur 15s
# 等 2 分钟
./loadtest -url https://... -token <令牌> -steps 1000 -step-dur 15s
```

## 已知限制

- **偶发的假失败**：连续切换场景时可能命中 TLS 重连或代理限流，个别轮次会出现 0 QPS 的异常行。重跑即可确认；出现明显偏离时以重测值为准。
- **soak 场景**只做延迟趋势对比（首段 vs 末段 P99），不采集服务端内存，判断内存泄漏还需结合服务端监控。
- **不支持自定义样本文本**：内置语料为通用中文短句与长文本，若要压特定业务文本，需修改 `main.go` 里的 `fillers`。
